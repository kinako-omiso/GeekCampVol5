# 3DScanPlan

## 目的

この文書は、実物スキャン対戦ゲームにおける3Dスキャン機能の実装計画を定義する。

最終的には、スマートフォンで複数方向から撮影した実物を、PCブラウザ上で実際の奥行きを持つ3Dモデルへ復元し、その形状をゲーム内の「コマ」として利用することを目標とする。

ただし、最初からSfMやVisual Hullをすべて実装するのではなく、以下の順序で段階的に検証する。

1. **最小構成：写真1枚から輪郭を押し出して3Dモデルを作る**
2. **SfMなし：既知のCamera Poseと複数SilhouetteからVisual Hullを作る**
3. **SfMあり：Camera Poseを自動推定し、Real Scanへ発展させる**

これにより、各段階で問題の原因を切り分けながら実装できる。

---

# 1. プロジェクト概要

本プロジェクトは、

> 身の回りの物体をスマートフォンでスキャンし、その形状から能力値を生成して、3Dのコマとして2人で戦わせるブラウザゲーム

である。

対象物の例：

- 消しゴム
- マグカップ
- ペットボトル
- マウス
- ぬいぐるみ
- 文房具
- スマートフォン
- 箱状の日用品

スマートフォンは、コントローラー兼スキャナーとして使用する。

ゲーム本体はPCブラウザで動作し、PC画面に表示したQRコードをスマートフォンで読み取って参加する。

# 3. 3Dスキャンの段階的な実装方針

3Dスキャン機能は、以下の3段階で実装する。

## Stage 1：Quick Scan 最小構成

最初の最小構成では、

```text
写真1枚
↓
対象物のSilhouette / Mask
↓
2D輪郭抽出
↓
一定厚みで押し出し
↓
3D Mesh
↓
Babylon.js表示
```

という方式を実装する。

これは厳密な三次元復元ではない。

目的は、

- 写真から3D Meshを生成する処理経路を確立する
- Babylon.jsへ動的Meshを渡す
- positions / indices / normals の生成を確認する
- geometry-wasmへ渡せる形式を確定する
- 後続のVisual Hull実装で再利用できるインターフェースを作る

ことである。

### Stage 1ではやらないこと

- SfM
- Visual Hull
- 複数視点
- Camera Pose
- テクスチャ
- Vertex Color
- 高精度形状復元

まずは、

> 1枚のSilhouetteから押し出し3Dモデルを生成してPCブラウザで表示できる

ところまでを最初の成功条件とする。

## Stage 2：Visual Hull PoC（SfMなし）

Stage 1が動作した後、

```text
複数Silhouette
+
既知のCamera Pose
↓
96³ Voxel Grid
↓
Silhouette Carving
↓
Visual Hull
↓
Marching Cubes
↓
3D Mesh
↓
Babylon.js表示
```

を実装する。

この段階ではCamera Poseを自動推定しない。

例：

```text
front =   0°
right =  90°
back  = 180°
left  = 270°
```

など、固定または手入力されたCamera Poseを使う。

目的は、

> Visual Hullという復元方式そのものが、このゲームのコマとして使える品質になるか

を検証することである。

SfMを後回しにすることで、

- Camera Pose推定の失敗
- Visual Hullの失敗
- Projection Matrixの誤り
- Voxel Carvingの誤り
- Mesh生成の誤り

を切り分けやすくする。

### Issue #32 で採用する Stage 2 の入力と実装

PCの `/dev/visual-hull` で正面・右・背面・左を必須、斜め4方向を任意とする写真4〜8枚を一括取込する。取込後は全写真の一覧から正面を利用者に選ばせる。選んだ写真を正面へ、残りを元の読込順で各方向へ割り当て、正面写真だけを大きく表示する。利用者の対象指定で正面Maskを作る。成功後は正面Maskの位置・大きさ・明るさ・彩度・輪郭を手掛かりに他方向の候補点を画像内容から探し、各写真で最大3点を既存のMediaPipe Interactive Segmenterに試す。空・端接触・面積差・低確信度を要確認として残し、失敗した写真だけ個別に修正する。同じ写真の候補は同じWorker内で処理し、`setImage()`を繰り返さない。固定方位角から透視Camera Poseを作り、利用者が方位角と写真の割当を修正できる。カメラは同じ高さ・距離で、対象を回す撮影を前提とする。

解像度は96³に固定し、二値面を標準とする。境界補間面は同じMaskから96³で比較できる。128³以上の生成・読込処理は設けない。投影範囲、Maskとの再投影輪郭、占有Voxel、メッシュ・形状解析・能力値、各段階の時間を表示する。写真・Mask・方位角・モデル・計測値はJSONに保存して再読込する。Mask確定後から表示までのp95が5秒以内という性能目標を記録する。2 Workerは4枚・8枚で25%以上の短縮とメモリの確認後に限る。実物評価は `07-visual-hull-evaluation.md` に記録する。

Voxel Carving と Marching Cubes は新設の `reconstruction-wasm` のC++で実装する。Quick ScanとVisual Hullは共通メッシュ形式を返し、`geometry-wasm` の3D形状解析と暫定能力値生成に接続する。WasmはEmscripten 6.0.10でローカルビルドし、生成物をリポジトリで管理する。品質評価の記録は `07-visual-hull-evaluation.md` を参照する。

## Stage 3：Real Scan（SfM追加）

Stage 2のVisual Hull PoCが成功した場合のみ、SfMを追加する。

```text
スマホで複数方向から撮影
↓
Feature Detection
↓
Feature Matching
↓
Essential / Fundamental Matrix
↓
Camera Pose
↓
Triangulation
↓
Bundle Adjustment
↓
Camera Pose確定
↓
Visual Hull
↓
3D Mesh
```

SfMの目的は、

> Dense 3D Reconstructionではなく、各撮影画像のCamera Poseを求めること

に限定する。

初期段階では以下は実装しない。

- Dense MVS
- Dense Point Cloud
- Depth Map
- Poisson Reconstruction
- NeRF
- Gaussian Splatting

# 4. Quick Scanの最小実装

最初に実装するQuick Scanは、写真1枚から対象物の輪郭を取得し、その輪郭をZ方向へ押し出して3D Meshを生成する。

概念：

```text
2D contour

(x0, y0)
(x1, y1)
(x2, y2)
...

↓ Extrude

front : z = +depth / 2
back  : z = -depth / 2
```

前面・背面・側面を生成する。

出力形式は将来のVisual Hullと共通化する。

```ts
type ReconstructionResult = {
  positions: Float32Array;
  indices: Uint32Array;
  normals?: Float32Array;
};
```

Stage 1の検証画面はPCで写真ファイルを1枚入力する。MaskはMediaPipeで生成し、再構成関数および合成Maskテストの入力とする。Maskファイルを直接入力するUIは設けない。

### 厚み

現行仕様に合わせ、基本値は

```text
最長軸の25%
```

程度とする。

### 最初の表示

- #dddddd の単色Material
- 前後面と側面はそれぞれ平面法線
- 体積重心を軸にモデルをドラッグで回転し、ホイールでモデルを拡大縮小する。カメラと光源は固定
- Textureなし
- UVなし

とする。

Stage 1からテクスチャに時間を使わない。

---

# 5. Visual Hullの基本方針

Stage 2では、複数のSilhouetteから3D形状を復元する。

3D空間をVoxel Gridとして表現する。

初期値：

```text
96 × 96 × 96
```

総Voxel数：

```text
884,736
```

各Voxelを各Cameraへ投影し、

```text
Voxel
 │
 ├── Camera A → Silhouette内？
 ├── Camera B → Silhouette内？
 ├── Camera C → Silhouette内？
 └── Camera D → Silhouette内？
```

すべてのCameraでSilhouette内部にあるVoxelだけを残す。

1つでもSilhouette外なら削除する。

---

# 6. Voxel Grid

最初は、

```text
96³
```

で固定する。

理由：

- 64³より形状品質が期待できる
- 96³で形状品質と処理量を両立できる
- 約88万VoxelなのでPoCとして扱いやすい
- PCブラウザ / Wasmで十分検証可能な規模

占有状態は、

```text
Uint8Array
```

などで保持する。

必要になるまでFloat32の距離場などは導入しない。

解像度の切替機能は設けず、96³に固定する。

---

# 7. Camera Model

Visual Hullに必要なCamera情報を、将来SfMの出力をそのまま接続できる形式で定義する。

候補：

```ts
type ReconstructionCamera = {
  intrinsics: Float32Array;
  rotation: Float32Array;
  translation: Float32Array;
  imageWidth: number;
  imageHeight: number;
};
```

必要な概念：

```text
K : Camera Intrinsics
R : Rotation
t : Translation
P : Projection Matrix
```

Stage 2ではCamera Poseを固定値または手入力で与える。

SfM追加後は、同じデータ構造へ推定結果を入れる。

---

# 8. Projection

各Voxelの3D座標をCamera画像へProjectionする。

概念：

```text
X_world
↓
R, t
↓
X_camera
↓
K
↓
pixel (u, v)
```

Projectionされた座標について、

- 画像範囲内か
- Silhouette Mask内か

を確認する。

Stage 2ではProjectionの正しさを確認するため、デバッグ表示を用意することを推奨する。

例：

- 投影点の画像表示
- Camera Frustum表示
- 一部Voxelだけを可視化
- Slice表示

---

# 9. Silhouette Carving

各Voxelに対して全Cameraを評価する。

疑似コード：

```text
for each voxel:
    occupied = true

    for each camera:
        pixel = project(voxel, camera)

        if pixel is outside image:
            occupied = false
            break

        if silhouette[pixel] == background:
            occupied = false
            break

    if occupied:
        keep voxel
```

PoCではまず単純実装を優先する。

高速化は、正しい形状が出ることを確認してから行う。

---

# 10. Mesh生成

Visual Hullで残ったVoxel VolumeからSurface Meshを生成する。

第一候補：

```text
Marching Cubes
```

出力：

```ts
type ReconstructionResult = {
  positions: Float32Array;
  indices: Uint32Array;
  normals?: Float32Array;
};
```

生成したMeshは、

- Babylon.js
- geometry-wasm

の両方へ渡せる形式にする。

Normalsを生成してSmooth Shadingする。

# 11. 表面表示

最初のPoCでは単色Materialのみ使用する。

実装しない：

- Texture Mapping
- UV展開
- Texture Atlas
- Multi View Texture Blending
- Vertex Color

理由：

> まず形状そのものが十分な品質か確認するため。

色や写真テクスチャによって形状精度の不足を隠さない。

# 12. 将来の色付け

Visual Hullの品質が十分だった場合、次にVertex Colorを検討する。

候補方式：

```text
Mesh Vertex
↓
各Cameraとの向きを比較
↓
最も正面から見ているCameraを選択
↓
そのCamera画像へProjection
↓
RGB取得
↓
Vertex Color
```

最初からUV MappingやTexture Atlasへ進まない。

優先順位：

```text
1. 単色
2. Vertex Color
3. 必要ならTexture
```

とする。

---

# 13. Visual Hullで期待する品質

Visual Hullはフルフォトグラメトリではない。

比較的再現しやすい：

- 消しゴム
- 箱
- ペットボトル
- スマホ
- マウス
- ぬいぐるみ

比較的難しい：

- マグカップ
- フォーク
- ハサミ

非常に難しい：

- 細いケーブル
- 透明物
- 細すぎる形状
- 強い反射を持つ物体

また、

> Silhouetteに現れない凹み

は原理的に復元できない。

例：

- ボウル内部
- 深い溝
- 表面の小さな凹凸
- ボタン
- ネジ穴

これはバグではなくVisual Hull方式の制約である。

---

# 14. 目標品質

目標は高精度3Dスキャナと同等のDigital Twinを作ることではない。

成功条件は、

> 元の物体を知っている人が、生成されたモデルを360°回転させたとき、何の物体かすぐ分かること。

例：

```text
消しゴム
→ 箱型の消しゴムとして認識できる

ペットボトル
→ 円筒、肩、奥行きが分かる

マウス
→ 丸みと左右の広がりが分かる

ぬいぐるみ
→ 頭、胴、手足の形が分かる

マグカップ
→ 本体と取っ手がおおむね分かる
```

ゲーム用途なので、細部の完全再現より、

- シルエット
- 奥行き
- 全体の立体形状

を優先する。

# 15. reconstruction-wasm

将来的には既存のgeometry-wasmと責務を分離する。

理想構成：

```text
packages/

web
protocol

reconstruction-wasm
├─ extrusion
├─ visual hull
├─ voxel carving
├─ marching cubes
└─ 将来的にSfM

geometry-wasm
├─ normalization
├─ convex hull
├─ center of mass
├─ inertia
├─ shape axes
└─ fighter stats
```

関係：

```text
reconstruction-wasm
        │
        │ positions / indices
        ▼
geometry-wasm
        │
        ▼
Babylon.js / Game
```

ただし、既存リポジトリを確認し、新規Packageが過剰ならPoC段階では最小構成を優先する。

# 16. geometry-wasmとの接続

既存の形状解析APIは概ね、

```ts
type GeometryInput = {
  positions: Float32Array;
  indices: Uint32Array;
  source: "photo" | "glb";
};
```

という構成を想定している。

Quick ScanでもVisual Hullでも、最終的には

```text
positions
indices
```

を出力する。

したがって、後段の形状解析は共通化する。

将来的には、

```ts
source: "photo" | "reconstruction" | "glb"
```

などへの変更を検討できる。

ただし、PoCでは既存APIを不必要に破壊しない。

8. Quick Scan PoCをどこへ追加するのが最小変更か判断する
9. Visual Hull PoCをどこへ追加するのが最小変更か判断する

# 特に検討してほしいこと

## A. Stage 1の押し出し処理をどこで行うか

候補：

```text
TypeScript
```

または

```text
C++ / WebAssembly
```

Issue #2のStage 1ではTypeScriptで押し出しMeshのpositions / indices / normalsを直接生成する。Babylon.jsは表示を担当し、geometry-wasmとの実接続はPhase 2に分ける。

Stage 2以降でreconstruction-wasmを導入するかは、Visual Hullの処理量と既存構成を確認して判断する。

## B. Visual Hullをどこで計算するか

候補：

```text
TypeScript
```

または

```text
C++ / WebAssembly
```

96³程度ならTypeScriptでもPoCできる可能性がある。

ただし、

- 約88万Voxel
- 複数Camera Projection
- 将来のSfMとの統合
- C++形状処理との親和性

を考えるとC++ / Wasmが有力。

最初から決め打ちせず、現在のプロジェクト構造と実装コストから判断する。

## C. Marching Cubes

候補：

- 自前実装
- 軽量な既存ライブラリ
- Babylon.js側で利用可能な機能

を比較する。

条件：

- 巨大な依存を追加しない
- positions / indicesを直接取得できる
- Wasmで利用可能
- 96³の固定解像度で処理できる

こと。

## D. Camera Model

Visual Hullに必要なCamera Modelを、将来SfM出力を接続できる形式で定義する。

必要な情報：

```text
K : Intrinsics
R : Rotation
t : Translation
P : Projection Matrix
```

ただし、Stage 2では固定Camera Poseのみ使用する。

SfMの都合でStage 2のAPIを全面変更することがないように設計する。

## E. Quick ScanとReal Scanで共通化する部分

共通化候補：

```text
ReconstructionResult
positions
indices
normals

↓
geometry-wasm

↓
Babylon.js
```

つまり、

```text
Quick Scan
     ┐
     ├─→ ReconstructionResult
     │          ↓
Real Scan      geometry-wasm
                ↓
              Game
```

という構成にする。

スキャン方式ごとにゲーム側の処理を分岐させすぎない。

## F. デバッグ方法

3D Reconstructionは途中結果が見えないと原因特定が難しい。

Stage 2では以下のデバッグ表示を検討する。

- Camera位置
- Camera Frustum
- Voxel Grid Bounding Box
- Occupied Voxel数
- Voxel Slice
- Projection Point
- Silhouette Mask
- Generated Mesh
- Normal表示

最初からすべて作る必要はないが、Camera ProjectionとVisual Hullの確認に必要な最低限の可視化を用意する。


```text
Visual Hull Mesh
```

まで確認する。

複数種類の物体で比較する。

- 箱
- 消しゴム
- ペットボトル
- マウス
- ぬいぐるみ
- マグカップ

確認項目：

- 元の物体として認識できるか
- 奥行きが自然か
- 細い部分が残るか
- 96³で十分か
- 処理時間
- Meshサイズ
- geometry-wasmで正常解析できるか

ここまで成功してからSfMへ進む。

# 最終目標

最終的な3Dスキャン処理は、

```text
スマートフォンで対象物の周囲を撮影
            │
            ▼
      Silhouette生成
            │
            ▼
      SfM Camera Pose
            │
            ▼
       Visual Hull
            │
            ▼
      96³以上のVolume
            │
            ▼
      Surface Mesh
            │
            ▼
      geometry-wasm
            │
            ├─ 正規化
            ├─ 凸包
            ├─ 重心
            ├─ 慣性
            ├─ 形状特徴
            └─ Fighter Stats
            │
            ▼
       Babylon.js / Game
```

とする。

ただし、実装は必ず以下の順序で進める。

```text
1. 写真1枚から押し出し3D
            ↓
2. SfMなしのVisual Hull
            ↓
3. SfMありのVisual Hull
            ↓
4. 必要ならVertex Color
            ↓
5. ゲーム本体へ統合
```

最初のゴールは、

> **1枚の写真またはSilhouetteから押し出し3Dモデルを生成し、Babylon.jsで単色表示すること。**

次のゴールは、

> **複数方向のSilhouetteと既知Camera Poseから、PCブラウザ上で96³ Visual Hullを生成し、単色3Dモデルとして360°確認できること。**

その2つが成功してから、

> **SfMを追加してCamera Poseを自動取得し、スマホ撮影からReal Scanまでを自動化する。**

Codexは、まずリポジトリ全体と既存ドキュメントを読み、現在のコード構造を把握すること。

その後、

1. Stage 1を最小変更で実装する計画
2. Stage 2へ拡張するためのインターフェース設計
3. 変更対象ファイル
4. 新規ファイル
5. 依存関係
6. テスト方法

を提示する。

**計画を提示する前に大規模なコード変更を開始しないこと。**
